# Устройство API

[Запуск приложения](../README.md) · [Разработка интерфейса и проверки](../docs/development.md)

FastAPI принимает запросы, SQLModel описывает данные и работает с SQLite.
Все прикладные маршруты начинаются с `/api`; интерактивная документация доступна на `/docs`.

Файлы `__init__.py` служат для организации Python-пакетов, прикладной логики в них нет.

## Как проходит запрос

`router.py` описывает HTTP-маршрут. FastAPI проверяет входные данные по модели и выполняет
зависимости `Depends(...)`: получает сессию БД и проверяет пользователя. Затем обработчик
вызывает нужные функции сервиса, сохраняет изменения и возвращает ответ по публичной модели.

Например, при `PATCH /api/users/3`:

1. `get_current_user()` проверяет JWT и активность отправителя в БД.
2. `require_permission('users.manage')` проверяет разрешение его роли.
3. `user_admin/router.py` проверяет ограничения и изменяет аккаунт №3.
4. `public_user()` возвращает профиль с названием роли и разрешениями, без пароля и хеша.

В JWT хранятся ID пользователя, время выдачи и срок действия. Роль и права читаются из БД,
поэтому блокировка и отзыв разрешений действуют на уже выданные токены.

## Маршруты

| Метод и путь | Назначение и доступ |
|---|---|
| `GET /api/auth/config` | Публичный флаг `registration_enabled` |
| `POST /api/auth/register` | Самостоятельная регистрация, если включена |
| `POST /api/auth/login` | Вход; принимает форму с `username` и `password`, возвращает JWT |
| `GET /api/auth/me` | Профиль текущего вошедшего пользователя |
| `GET /api/users`, `POST /api/users`, `PATCH /api/users/{id}` | Управление аккаунтами: разрешение `users.manage` |
| `GET /api/roles` | Список ролей для любого вошедшего пользователя |
| `GET /api/roles/permissions` | Каталог разрешений для суперадминистратора |
| `POST /api/roles`, `PATCH /api/roles/{id}`, `DELETE /api/roles/{id}` | Изменение ролей только суперадминистратором |

Остальные запросы с телом принимают JSON. Защищённые запросы требуют `Authorization: Bearer <токен>`.

## Роли и разрешения

У пользователя одна роль, у роли — список ключей разрешений в JSON-колонке.
Идентификатор роли хранится у пользователя строкой; существование роли проверяет приложение.

- Самостоятельная регистрация назначает `user`. Эту роль нельзя удалить, её название и разрешения редактируются.
- `superadmin` нельзя изменить или удалить; он автоматически получает весь каталог `PERMISSIONS`.
- `admin` — обычная начальная роль без дополнительных разрешений. Создаётся при первой инициализации; после удаления не восстанавливается.
- Занятую роль нельзя удалить, пока её пользователям не назначена другая роль.
- Нельзя сменить собственную роль или заблокировать себя. Управлять суперадминистраторами может только суперадминистратор.

Для новой возможности добавьте ключ и подпись в `PERMISSIONS` в `modules/roles/models.py`.
Ключ появится в редакторе ролей. Сервер защищается через `Depends(require_permission('tasks.manage'))`,
ограничение страницы задаётся [на фронтенде](../docs/development.md#отключить-страницу-или-скрыть-ссылку).
`require_roles('superadmin')` используется для действий, доступных только системной роли.

## Настройки

Python читает окружение. При Docker-запуске корневой Compose передаёт настройки из `.env`;
сам `config.py` файл `.env` не загружает. Новую переменную для контейнера нужно также передать в Compose.

| Настройка | Назначение |
|---|---|
| `SECRET_KEY` | Обязательный ключ подписи JWT |
| `DATABASE_URL` | Подключение в `core/db.py`; по умолчанию SQLite в `/api/data/db.sqlite3` |
| `REGISTRATION_ENABLED` | Регистрация включена по умолчанию; `false` скрывает кнопку и запрещает API-запрос с 403 |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD` | Начальные данные аккаунта из [инструкции запуска](../README.md#первый-запуск) |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Срок JWT, по умолчанию 1440 минут; сейчас не передаётся корневым Compose |

Чтобы отключить регистрацию, установите `REGISTRATION_ENABLED=false` в `.env`, выполните
`docker compose up -d api` и обновите страницу. Для обычного режима используйте
`docker compose -f compose.yaml up -d api`. Пересборка фронтенда не нужна.
Вход и создание аккаунтов администратором продолжают работать. Если интерфейс не получил
настройки, регистрация скрыта до обновления страницы, вход остаётся доступен.

Пароли хранятся как Argon2id-хеши; при создании требуется 8–128 символов.
Изменение начальных данных не перезаписывает существующий аккаунт. Пустой начальный логин
или пароль отключает его создание.

## Добавить серверный модуль

Создайте `modules/tasks/router.py` с `router = APIRouter(prefix='/tasks')`.
Модели БД при необходимости разместите рядом и импортируйте в роутере.
Подключите модуль в `main.py` до создания таблиц:

```python
from modules.tasks.router import router as tasks_router
```

После создания `app` добавьте:

```python
app.include_router(tasks_router, prefix='/api')
```

Для запроса, требующего только входа, используйте `Depends(get_current_user)`;
для ограничения по разрешению — `Depends(require_permission('tasks.manage'))`.
Обе зависимости находятся в `modules/users/dependencies.py` и возвращают текущего пользователя.
Сессию БД предоставляет `Depends(get_session)` из `core/db.py`.
Чтобы отключить API модуля, удалите импорт и подключение роутера; данные останутся в БД.

## База и ограничения

`main.py` при импорте создаёт отсутствующие таблицы и запускает инициализацию ролей и аккаунта.
В контейнере `/api/data` связан с локальной папкой `db`. Существующие роли и аккаунты при запуске не перезаписываются.

Миграций схемы нет: `create_all()` не добавляет колонки в существующие таблицы.
После изменения схемы одноразовую тестовую БД можно пересоздать, остановив приложение и удалив
`db/db.sqlite3`. Для ценных данных понадобится миграция. Пагинации, истории административных действий,
ограничения частоты входа и автоматических резервных копий пока нет.

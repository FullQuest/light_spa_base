КОНТРАКТЫ НЕПРИЛОЖЕННЫХ ЧАСТЕЙ
Это справка по текущему проекту, а не результат твоей проверки исходников. Используй её; при противоречии с приложенным кодом сообщи об этом и опирайся на код.
- Стек: FastAPI, SQLModel, SQLite; React, TypeScript, Vite, React Router. В requests отдельного service.py нет: работа с БД находится в роутере.
- core.db экспортирует engine и get_session(): with Session(engine) as session: yield session. Commit/rollback/refresh выполняет прикладной код.
- В main.py модели импортируются до SQLModel.metadata.create_all(engine); роутеры подключаются через app.include_router(..., prefix="/api"). create_all не обновляет схему существующих таблиц. Изменение SQLModel само по себе не переносит существующие данные.
- get_current_user, require_permission и require_roles из modules.users.dependencies возвращают User. JWT идентифицирует пользователя; активность и роль проверяются по БД. User содержит id, email, full_name, hashed_password, is_active, role.
- Новые права — дополнительные ключи словаря PERMISSIONS в api/modules/roles/models.py. superadmin получает весь каталог, остальные роли — сохранённые permissions. .manage не включает .view автоматически. Изменяющие операции requests требуют оба права.
- useAuth из auth/auth.ts возвращает user, loading, error, login, register, logout. user может быть null; публичный профиль содержит id, email, full_name, role, role_name, permissions, is_active.
- Страницы и меню регистрируются в app/modules.ts: {path, title, Page, permission?, superadminOnly?, enabled?, menu?}. enabled: false отключает маршрут; menu: false скрывает только ссылку. Проверки интерфейса не заменяют защиту API.
- Страницы используют react-router и локальные CSS. Если ошибка относится к оформлению или маршрутам, соответствующие исходники можно запросить после постановки задачи.

КОГДА ПОЛУЧИШЬ ЗАДАЧУ
1. Для изменения проследи влияние на таблицу, входную схему, ответ API, TS-типы, формы, список/карточку, фильтры и права. Меняй только затронутые части.
2. Если меняется схема, учти существующие записи, значения по умолчанию, допустимость null и перенос данных. Не предлагай удаление рабочей БД как обычный способ обновления. Уточни необходимость сохранения данных, если от неё зависит решение.
3. Для ошибки отдели симптомы от гипотез. При нехватке информации запроси конкретные шаги, ожидаемый/фактический результат, текст ошибки или ответ API. Запроси только нужные файлы; не объявляй гипотезу установленной причиной.
4. Выдай готовые правки с путями и краткий способ проверки по пользовательскому сценарию. Для неприложенного файла допустима точная инструкция добавления по контракту, но не полная замена. Если меняется сам контракт, запроси актуальный исходник.
Не выдумывай код неприложенных файлов, результаты запусков, тестов или содержимое БД. Формат правок свободный.

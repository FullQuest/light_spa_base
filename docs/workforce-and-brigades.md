# Рабочие и формирование бригад

Модуль 2: `/workers` — полный список рабочих без пагинации, `/brigades` — результат формирования.
Обе страницы доступны вошедшим пользователям. Синхронизация PostgreSQL и оптимизатор разрабатываются отдельно.

## Рабочие

Поля соответствуют таблицам `employee` и `qualification` из нового `backup.sql`:
табельный номер (первичный ключ рабочего), фамилия, имя, отчество, дата начала стажа,
стаж в полных годах и пары «ID квалификации / уровень» для каждого ресурса.
`id_employee` квалификации совпадает с табельным номером строки. Ресурсы добавляются
динамически; отсутствие квалификации обозначается «—», а не нулём.

Каждый столбец сортируется по нажатию на заголовок. Для текста доступен поиск части строки,
для чисел и дат — включительные границы «от / до», для квалификаций — фильтр отсутствия.
Условия сочетаются между собой и с общим поиском. Отсутствующие числовые значения остаются
в конце при обоих направлениях сортировки. Даты и стаж определяются по Москве.

XLSX включает текущие отфильтрованные строки в выбранном порядке. Цвета разделяют
общие поля, воду и электроэнергию; строки чередуются. Числа экспортируются числами,
даты — отображаемым текстом. Зависимость `write-excel-file` загружается только при экспорте.

## Результат формирования

- Кнопка запускает задачу и показывает полученный прогресс; `progress: null` означает
  неопределённый прогресс. Опрос последовательный, один запрос за раз, интервал 500 мс.
- Последний успешный результат остаётся виден при повторном запуске и сохраняется при ошибке.
  Выгрузка заблокирована во время расчёта и при обнаружении некорректного результата.
- Иерархия раскрывает бригаду, порядок работ и полный состав с датой стажа, квалификациями и ID.
- Сводное расписание содержит все поля ТЗ; каждый столбец сортируется.
- Диаграмма использует общую шкалу времени, дорожку на бригаду, цвета ресурсов,
  прокрутку, масштаб 100/200/400% и подробности при нажатии на блок.
  Короткие блоки имеют минимальную видимую ширину; визуально пересекающиеся блоки
  размещаются на разных строках внутри дорожки. Некорректные интервалы сохраняются
  в таблице с предупреждением, но не рисуются на диаграмме.
- «Фактическое время» — прогноз длительности работы бригады из ответа алгоритма,
  не телеметрия ремонта. Время в интерфейсе отображается явно в МСК.
- Фильтры по бригаде, ресурсу и объекту/событию действуют на все три представления.
  JSON всегда содержит полное решение, независимо от визуальных фильтров.

## Подключение API

Точка замены транспорта — `frontend/src/modules/brigades/api.ts`, типы — `types.ts`
в `brigades/` и `workforce/`. По умолчанию используется отдельный mock-адаптер:
28 рабочих и 42 квалификации взяты из предоставленного дампа, расписание синтетическое.
Оно предназначено для проверки интерфейса и не является результатом оптимизации.
Mock хранит задачи/результаты в браузере, отдельно по ID пользователя. Для реального
API задайте `VITE_REPAIR_API_MODE=http` в окружении Vite или `frontend/.env.local`
и перезапустите dev-сервер (для production — пересоберите).

Предлагаемый контракт (сервер пока не реализован):

| Метод и путь | Ответ |
|---|---|
| `GET /api/workforce/employees` | `Employee[]`, вложенные `qualifications` |
| `GET /api/brigades/result` | `FormationResult` или JSON `null`, если результата нет |
| `GET /api/brigades/jobs/current` | `FormationJob` или JSON `null` |
| `POST /api/brigades/jobs` | `FormationJob`, начало расчёта |
| `GET /api/brigades/jobs/{id}` | `FormationJob`, состояние, прогресс и итог |

`FormationJob`: `id`, `status` (`running/completed/failed`), `progress` (0–100 или null),
`stage`, необязательные `error` и `result`. Завершённая задача должна содержать `result`.
`FormationResult`: `id`, `generatedAt`, `dataRevision`, `employees`, `brigades`, `incidents`.
Сроки — ISO 8601 с offset или `Z`, длительности — числовые секунды (допускаются доли).
`sequence` — порядок инцидента внутри бригады, начиная с 1.

Файл `brigades.json` создаётся строго в формате M2, без служебных данных:

```json
{"brigades":[{"brigade_id":1,"employees":[610001,610003],"event_order":[501,503]}]}
```

После успешного `/api/infra-loader/delete-all` интерфейс вызывает `invalidateFormationResults()`:
удаляет локальный JSON/результат и задачи, обновляет ревизию, уведомляет открытые вкладки,
прерывает текущие клиентские запросы. Ошибка очистки сохраняет предыдущий результат.
Будущий backend обязан в той же операции удалять серверный результат и отменять/инвалидировать
старые задачи по ревизии, чтобы очистка действовала для других браузеров и после нового входа.
При загрузке другого набора данных нужно также менять `dataRevision` и инвалидировать старый результат.

## Проверки

```sh
docker compose exec -T frontend npm run lint
docker compose exec -T frontend npm run build
docker compose exec -T frontend npm run test:operations
```

Тесты данных проверяют числовую сортировку и отсутствующие квалификации, сочетание фильтров,
календарный стаж, формат M2, интервалы и пересечения, ожидание/занятость, 10 000 событий.

MCP Playwright: все фильтры/сортировки, XLSX и JSON, иерархия/составы, обе темы, ширины
390/768/1920 px, масштаб, клавиатура, пустые/длинные/неизвестные значения, нулевые и короткие
работы, десятидневный период, пересечения, ошибочные даты, 40 бригад / 800 инцидентов,
перезагрузка расчёта, сохранение прежнего результата при ошибке, очистка из другой вкладки
и предотвращение возврата старого результата выполняющейся задачей. Очистка проверяется
с перехватом HTTP-запроса, без удаления пользовательской БД. Локальные артефакты — `.playwright-mcp/`.

# План работы с чёрным ящиком

Этот документ описывает, как использовать ограниченное число отправок JSON в сервис
организаторов, если матрица конфликтности рабочих недоступна. Цель — получить хорошее
разбиение рабочих и расписание, а не попытаться полностью восстановить скрытую матрицу.

Текущая точка отсчёта — [test_brigades.json](../test_brigades.json), который создаётся
скриптом [tools/generate_test_brigades.py](../tools/generate_test_brigades.py). Это
валидное, но намеренно простое решение для исходного `backup.sql`: 7 бригад по 4 рабочих,
45 активных событий распределены в топологическом порядке. Его нужно сохранить как
контрольный кандидат и не менять во время экспериментов.

## Что именно вычисляет проверяющий сервис

Для бригады `B` и инцидента с ресурсом `r` из ТЗ следует модель:

```text
S(B, r) = Σ qualification(worker, r) / 5
T(B, incident) = (1 + Kmax(B)) · Tbase(incident) / S(B, r)
```

Если у рабочего нет квалификации по ресурсу инцидента, его вклад равен нулю.
`Kmax(B)` — максимальная конфликтность среди **всех** пар рабочих бригады, даже если
они не имеют квалификации по текущему ресурсу. Для 2–5 рабочих это максимум среди
1–10 пар. Конфликтность симметрична и постоянна, но значения скрыты.

После этого сервис строит расписание:

- бригада выполняет свои события последовательно;
- зависимое событие ждёт завершения всех необходимых событий-предшественников;
- разные бригады могут работать параллельно;
- итоговая цель — минимизировать момент завершения последнего события `Cmax`.

Итоговая оценка — это одно число времени и процент относительно эталона. Время нужно
считать главным измерением. Формулу процента сначала надо проверить на двух кандидатах:
обычно больший процент означает меньшее время, но нельзя зашивать это предположение
до первой калибровки.

## Почему полное восстановление матрицы почти невозможно

Для 28 рабочих существует 378 независимых пар. За 100–200 запусков нельзя надёжно
оценить каждую пару, особенно когда сервис возвращает только `Cmax`:

1. Итоговое время показывает только критическую бригаду или критическую цепочку.
   Изменение некритичной группы может вообще не изменить ответ.
2. Внутри одной бригады виден только максимальный конфликт. Если в группе есть пара
   с `K=0.8`, значения остальных пар не влияют на её время.
3. Квалификация, базовое время и зависимости меняют критический путь одновременно
   с конфликтом. Наблюдаемое ухудшение нельзя автоматически приписывать одной паре.
4. Время разных бригад объединяется операцией `max`, поэтому разница между двумя
   JSON может быть обрезана другой, более медленной бригадой.

Поэтому результат экспериментов должен быть не таблицей «точное `K(i,j)` для всех пар»,
а моделью полезности:

- пары, которые безопасно объединять;
- пары, которые стоит разводить по разным бригадам;
- устойчивые составы из 2–5 рабочих;
- приблизительный штраф группы, если она попадает на критическую работу.

## Что логировать после каждой отправки

Без журнала оценки быстро потеряют смысл. Для каждого JSON сохранять одну запись, например
в `experiments/results.jsonl` или CSV:

| Поле | Значение |
|---|---|
| `run_id` | последовательный номер запуска |
| `json_sha256` | хеш отправленного файла |
| `parent_id` | кандидат, из которого сделана мутация |
| `mutation` | `swap_workers`, `move_event`, `reorder`, `new_partition` и параметры |
| `elapsed_seconds` | время ответа сервиса |
| `reported_time` | итоговое время ликвидации |
| `score_percent` | процент от эталона |
| `valid` / `error` | результат проверки формата и правил |
| `brigade_signature` | отсортированные составы бригад |
| `event_signature` | порядок событий по бригадам |
| `notes` | гипотеза эксперимента |

Сам JSON тоже нужно складывать в каталог с именем вроде `run-0042.json`. Хеш защищает
от ошибки, когда результат в журнале случайно относится к другому файлу.

## Экспериментальный план на 100–200 запусков

### 0. Калибровка измерения — 5–10 запусков

1. Отправить контрольный `test_brigades.json` и записать время и процент.
2. Отправить 2–3 заведомо разных валидных решения: изменить только порядок событий,
   затем только разбиение рабочих. Это проверит, что сервис действительно учитывает
   обе части JSON.
3. Сделать 2 одинаковых отправки, если квота позволяет. Совпадение ответа проверит
   детерминированность сервиса; различия нужно учитывать медианой, а не одним числом.
4. Проверить направление процента: меньший `reported_time` должен давать более высокий
   результат. Если это не так, в оптимизаторе использовать время напрямую и процент
   только как дополнительную отметку.

### 1. Парные контрасты — 50–80 запусков

Не отправлять случайные JSON. Нужна пара кандидатов, отличающихся одной гипотезой:

- сохранить размеры бригад, события и все остальные составы;
- поменять местами двух рабочих между двумя бригадами;
- сохранить покрытие ресурсов: каждая изменённая бригада должна иметь хотя бы одного
  рабочего по воде и электроэнергии для событий, которые на неё назначены;
- сохранить порядок событий, кроме необходимых переносов.

Для пары `(A, B)` сравнивать не одно абсолютное время, а разность с тем же контрольным
кандидатом. Если замена повторяется в нескольких контекстах и ухудшает результат,
помечать сочетание как опасное. Если улучшает — как перспективное. Контекст важен:
одна и та же пара может быть видна только когда её бригада становится критической.

Приоритет пар для первых проб:

1. рабочие с высокой квалификацией по одному ресурсу, которые часто оказываются на
   длинных работах;
2. пары из универсального рабочего и узкого специалиста;
3. пары, которые сейчас находятся в одном составе контрольного решения;
4. пары из разных текущих бригад для swap-теста.

Для каждой пары недостаточно одного запуска. При бюджете 60 запусков лучше проверить
20 пар в трёх разных контекстах, чем 60 пар по одному разу.

### 2. Контраст составов — 20–30 запусков

Сравнивать не только пары, но и группы из 3–5 рабочих:

- один и тот же набор событий и размеры бригад;
- состав `A+B+C` против `A+B+D`;
- затем тот же состав на воде и на электроэнергии;
- отдельно проверить, что сильный конфликт в группе портит обе специализации, поскольку
  `Kmax` берётся без учёта ресурса.

Если группа с большим суммарным уровнем квалификаций проигрывает группе слабее, это
сильный признак скрытого конфликта. Но делать вывод нужно только после проверки,
что обе группы были критическими и имели сопоставимые зависимости.

### 3. Поиск расписания — 40–80 запусков

После первых контрастов зафиксировать 2–5 лучших разбиений и улучшать их локально:

- swap двух рабочих между бригадами;
- перенос события в другую совместимую бригаду;
- перестановка независимых событий внутри одной бригады;
- перенос длинной цепочки целиком, если это уменьшает критический путь;
- изменение размера состава с 4 до 3 или 5, когда это не нарушает покрытие навыков.

Использовать элитный набор из 5–10 лучших кандидатов и не терять контрольный JSON.
На каждом шаге оставлять несколько разных решений, а не только один текущий максимум:
чёрный ящик может давать одинаковое `Cmax` для разных локальных минимумов.

## Как оценивать скрытый конфликт

Если удалось создать кандидат, в котором известная бригада является единственным
критическим узким местом, можно получить грубую оценку:

```text
K приблизительно = Tнаблюдаемое · S(B, r) / Tbase(incident) - 1
```

Это работает только для изолированного события или заранее известного критического пути.
Для обычного полного расписания это верхняя оценка, смешанная с ожиданием зависимостей.
Нельзя использовать её как точное значение матрицы.

Практичнее поддерживать для пары диапазон и знак:

```text
pair(A, B) -> { better_than: [...], worse_than: [...], confidence: 0..1 }
```

Каждый swap обновляет сравнения, а не одно «истинное» число. Для выбора состава нужна
оценка риска группы, например максимум штрафа среди известных плохих пар плюс штраф
за неопределённые пары. Это естественно соответствует `Kmax` и защищает от неизвестной
конфликтной пары.

## Генератор кандидатов

Геном кандидата удобно разделить на две части:

```text
partition = [[employee_id, ...], ...]
schedule = [[event_id, ...], ...]
```

Генератор обязан проверять до отправки:

- каждый рабочий встречается ровно один раз;
- размер бригады от 2 до 5;
- каждая бригада получает хотя бы одно событие;
- каждое активное событие назначено ровно одной бригаде;
- для каждого события в бригаде есть хотя бы один рабочий с квалификацией ресурса;
- внутри каждой бригады порядок событий не создаёт запрещённое пересечение;
- зависимые события не поставлены раньше событий-предшественников, если они находятся
  в одной последовательности;
- JSON содержит только `brigades`, `brigade_id`, `employees`, `event_order`.

Для событий использовать топологическую сортировку текущего графа. При переносе события
в другую бригаду заново проверять зависимости; нельзя переносить старые ID событий
между наборами данных, потому что организаторы меняют объекты, связи и базовые времена.

## Как использовать новые наборы данных

По ТЗ при проверке могут измениться объекты, зависимости и `time_resolve`, но сохраняются
рабочие, квалификации и скрытая матрица конфликтов. Поэтому результаты экспериментов
по парам рабочих можно переносить между наборами, а расписание — нельзя.

На каждом новом наборе нужно заново:

1. загрузить рабочих и квалификации;
2. получить актуальные активные события, зависимости и базовые времена;
3. построить новый граф предшественников и новый список событий;
4. сохранить прежний рейтинг пар как prior, но снова проверить 5–10 лучших составов;
5. сформировать расписание с новыми ID и прогнать локальный поиск.

Если состав рабочих или квалификации всё-таки изменились, старый prior нужно отбросить.
Скрытая матрица не обязана переноситься на другого набора рабочих.

## Рекомендуемый бюджет

Для 150 отправок разумное начальное распределение выглядит так:

```text
  5  контроль и проверка детерминированности
 15  калибровочные решения по размерам и порядку
60  парные swap-контрасты
25  контрасты групп из 3–5 рабочих
35  локальный поиск по расписанию и разбиению
10  финальные независимые кандидаты
---
150  отправок
```

Финальные 10 кандидатов не должны быть только последними мутантами одного решения.
Включить лучший найденный вариант, лучший вариант без учёта конфликтов, контрольный
JSON и несколько решений с разными разбиениями. Это позволит понять, не оказался ли
локальный результат случайно хорошим из-за конкретного критического пути.

## Чего не делать

- Не пытаться перебрать все 378 пар и не считать отсутствие изменения ответа доказательством
  отсутствия конфликта.
- Не сравнивать JSON, в которых одновременно изменены состав, порядок и нагрузка:
  такой эксперимент ничего не объясняет.
- Не оптимизировать процент без записи исходного времени и не делать вывод по округлённому
  проценту.
- Не назначать все длинные события одной бригаде только ради наблюдаемости: такой кандидат
  может быть настолько плохим, что скрывает полезную разницу между парами.
- Не использовать старые `event_id`, если организаторы загрузили новый набор данных.
- Не отправлять невалидные JSON в сервис: ошибки формата не дают информации о чёрном ящике.

## Следующий шаг для изучения скрытых конфликтов

Локальный оптимизатор с нулевой матрицей уже описан в [README](README.md).
Для изучения скрытой матрицы отдельно нужен экспериментальный harness, который:

1. читает `backup.sql` и строит валидный baseline;
2. генерирует swap-кандидатов с сохранением ограничений;
3. сохраняет каждый JSON и метаданные запуска;
4. принимает вручную введённые `reported_time` и `score_percent` либо читает их из
   ответа сервиса;
5. строит таблицу сравнений и выдаёт следующие 5–10 наиболее информативных кандидатов.

Только после проверки harness на локальных данных стоит тратить квоту сервиса. Реальную
оптимизацию нужно запускать отдельным этапом после того, как станет понятен формат ответа
и ограничение на число отправок.

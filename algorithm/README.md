# Формирование бригад и расписания

Самостоятельный Python-модуль для М2 из [ТЗ](../tz2.md). Не импортирует FastAPI,
не подключается к БД приложения и не меняет интерфейс. Python 3.10+, внешних
библиотек не требуется. Для штатного состава рабочих `ConflictMatrix.zeros()` возвращает
встроенную матрицу конфликтов; для других составов используется нулевая матрица, если
внешний файл не передан.

Алгоритм ищет одновременно составы постоянных бригад, назначения инцидентов и очереди
работ. Цель — минимальный `Cmax`, время завершения последней работы. Для малых задач
включается полный поиск с отсечениями; для больших используется гибрид случайного поиска
и полного прохода по локальным перестановкам. На больших задачах оптимальность не
доказывается, если не достигнута корректная нижняя оценка. Локальная оценка с K=0 не
предсказывает результат скрытой матрицы организаторов.

## Запуск

Из корня репозитория:

```sh
# Маленький пример, полностью без Docker и PostgreSQL
python3 -m algorithm --input algorithm/examples/demo.json --seed 0 --output algorithm/output/demo-brigades.json --report algorithm/output/demo-report.json

# Реальный дамп и контрольный кандидат из репозитория
python3 -m algorithm --backup backup.sql --baseline test_brigades.json --seed 0 --time-limit 30 --output algorithm/output/brigades.json --report algorithm/output/report.json

# Только проверить и посчитать существующее решение
python3 -m algorithm --backup backup.sql --evaluate test_brigades.json --report algorithm/output/baseline-report.json

# Тесты
python3 -m unittest discover -s algorithm/tests -v
```

`backup.sql` — custom-архив PostgreSQL. Для его декодирования нужен `pg_restore` на
хосте, либо уже существующий контейнер `postgres-fixture`:

```sh
docker compose -f compose.yaml -f compose.override.yaml -f compose.postgres-test.yaml up -d postgres-fixture
```

CLI передаёт содержимое локального файла в `pg_restore` через stdin и **только читает**
результат `COPY`. SQL не исполняется, база не восстанавливается. Поддерживается также
обычный текстовый SQL-дамп с `COPY public.table (columns) FROM stdin`.

Без `--input/--backup` читается корневой `backup.sql`. По умолчанию поиск использует
полный бюджет в 30 секунд. Максимальный `--time-limit` — 170 секунд, с запасом под
ограничение ТЗ в 180 секунд на текущем наборе. Время чтения дампа не входит в бюджет
поиска. `--iterations` задаёт необязательный лимит шагов и выключает неограниченный режим;
фиксированные `--seed` и лимит шагов воспроизводят поиск, если он не остановлен по часам.
Для маленьких задач точный перебор автоматически прекращается по лимиту узлов/времени;
для остальных поиск сохраняет лучший допустимый результат на каждом шаге.

`--baseline` — необязательный валидный M2. Он участвует в поиске; результат не может
оказаться хуже него по времени. Контрольный `test_brigades.json` оставлен без изменений,
CLI запрещает перезаписывать его, входные данные и baseline выходом или отчётом.
Невозможная задача/невалидный вход дают код возврата 2 без записи нового решения.

## Вход и выход

Нормализованный JSON см. в [examples/demo.json](examples/demo.json):

- `employees`: `tabel` и `qualifications`, словарь `ресурс -> уровень 0.1..10`;
- `incidents`: `event_id`, `resource`, положительное `base_duration_seconds`;
  необязательные `object_id`, `occurred_at` — сведения для отчёта;
- `precedences`: пары `[source_event_id, dependent_event_id]` между активными инцидентами.

ID — положительные целые числа, не индексы массивов. Число рабочих, набор ресурсов,
число инцидентов и число бригад не зафиксированы. Отсутствующая квалификация даёт нулевой
вклад. Рабочие без квалификаций тоже включаются в бригады. Когда всех рабочих нельзя
разместить в бригадах 2–5 человек с хотя бы одним совместимым инцидентом, возвращается
явная ошибка. Ноль активных инцидентов также невозможен по условию «каждая бригада
получает работу»; приложение в будущем должно обрабатывать этот случай до оптимизатора.

Загрузчик дампа читает `employee`, `qualification`, `events`, `event_statuses`,
`time_resolve`, `edifice_dependencies`, обращается к столбцам по именам:

- выбирает последнее событие каждой пары объект/ресурс, затем оставляет активные аварии;
  исторические аварии, закрытые новым статусом, в решение не попадают;
- статус распознаётся по точному названию; для другого справочника есть повторяемый
  `--active-status-id`, молчаливого предположения «активный ID всегда 1» нет;
- `avg_resolution_time` переводится из PostgreSQL interval в секунды, включая дни и доли;
- зависимости применяются **в рамках ресурса связи**, как в существующем графе приложения;
- транзитивные пути учитываются даже через объекты без активного инцидента;
- `occurred_at` — история события, все выбранные аварии доступны в момент начала плана.
  Это не моделирование будущего потока аварий. Начало плана — относительный `t=0`.

`brigades.json` содержит строго M2: только `brigades`, `brigade_id`, `employees`,
`event_order`. Отчёт сохраняется отдельно: времена в секундах, порядок, Kmax,
нижняя оценка, история улучшений, seed и причина остановки. `gap_to_lower_bound_percent`
сравнивает с оптимистической нижней оценкой, а не с известным эталоном организаторов.
`algorithm/output/` исключён из Git.

Для подстановки реальной матрицы в будущем:

```json
{"employee_ids":[101,102],"values":[[0.0,0.3],[0.3,0.0]]}
```

Передайте файл через `--conflicts`. Матрица должна включать ровно текущих рабочих,
быть симметричной, иметь нулевую диагональ и значения 0..0.9. Порядок табельных номеров
может отличаться от порядка во входе. Матрица с двумя ID выше — только пример формата.

## Как устроен поиск

1. Проверяет вход, покрытие ресурсов и DAG инцидентов. Рассматривает все допустимые
   числа бригад от `ceil(N/5)` до `min(floor(N/2), число инцидентов, число совместимых пар)`.
   Верхний предел уточняет максимальное паросочетание рабочий/инцидент.
2. Создаёт разные разбиения: специализированные, сбалансированные и случайные.
   У каждой начальной бригады есть квалифицированный рабочий и отдельный совместимый инцидент.
3. Строит начальное расписание по длине оставшегося критического пути. Выбирает бригаду
   с самым ранним завершением, вставляет работы в свободные интервалы. Если остались
   пустые бригады, резервирует им различные совместимые работы через паросочетание.
4. На маленьких задачах перечисляет все допустимые разбиения и очереди с branch-and-bound;
   симметричные перестановки номеров бригад убираются. Для больших задач использует
   случайные мутации и несколько элитных разбиений, а также полные локальные проходы по
   обменам/переносам рабочих и инцидентов. Периодически перебирает составы пар бригад и
   переносит непрерывные блоки работ.
5. Оценивает каждое расписание по объединённому графу зависимостей и очередей бригад.
   Самый длинный путь задаёт точные ранние старты и `Cmax` для выбранного решения.
   Проверка объединённого графа отбрасывает также взаимоблокировки между бригадами.
6. Сохраняет лучший валидный вариант, допускает ожидание перед задачами и проверяет
   экспорт повторно публичным валидатором. Нижняя оценка объединяет критический путь,
   общую производительность и совместную пропускную способность работников по ресурсам.
   В отчёте `optimality_proven=true` выставляется только при совпадении допустимого
   решения с нижней оценкой либо после завершения полного перебора.

Для каждого инцидента длительность равна
`(1 + max(Kij среди всех пар бригады)) * Tbase / sum(Rworker,resource / 5)`.
Разные бригады работают параллельно, внутри одной бригады работы идут последовательно.
Число событий и идентификаторы из нового дампа каждый раз читаются заново.

## Карта файлов

| Файл | Назначение |
|---|---|
| `models.py` | Доменные модели, M2, нулевая/внешняя матрица |
| `input.py` | JSON, чтение дампа, интервалы, актуальные события, транзитивные зависимости |
| `solver.py` | Валидатор, точный оценщик, эвристический гибридный поиск, отчёт |
| `exact.py` | Полный поиск с отсечениями для малых задач |
| `__main__.py` | CLI, бюджеты, отдельный экспорт M2 и диагностики |
| `tests/` | Формула, DAG/взаимоблокировки, инварианты, паросочетания, маленький полный перебор |
| [black-box-plan.md](black-box-plan.md) | Будущие эксперименты по скрытым конфликтам |

## Проверенный результат

На текущем `backup.sql` со встроенной матрицей конфликтов, `seed=0` и без baseline
30 секунд поиска дали следующий результат:

| Кандидат | Бригады | Cmax |
|---|---|---|
| Контрольный `test_brigades.json` | 7 по 4 человека | 72 988.440 с — 20 ч 16 мин |
| Оптимизатор | 10, размеры 3/2/3/4/2/5/3/2/2/2 | 26 588.184 с — 7 ч 23 мин |

Снижение времени относительно контрольного решения — 63.57%. Нижняя оценка —
18 179.670 с, разрыв — 46.25%; это не доказательство оптимальности. Учтены 45 инцидентов
и 138 загруженных транзитивных предшествований. Старт/завершение каждой работы совпали
с независимой дискретно-событийной симуляцией, а малые синтетические задачи — с полным
перебором. Проверка скрытого сервиса организаторов не выполнялась. Результат зависит
от seed и машины.

Результат независимого Python-вызова: `optimize(problem, conflicts=None,
initial_solution=None, seed=0, iterations=None, time_limit_seconds=30)`.
Возвращает `OptimizationResult` с `solution`, `evaluation` и статистикой. Для проверки
чужого M2 есть `Solution.from_dict()` и `evaluate(problem, solution, conflicts=None)`.

Увеличение бюджета с 30 до 40 секунд на текущей встроенной матрице в проверочном прогоне
не изменило `Cmax`: оба запуска дали 26 588.184 с. Поэтому в CLI и серверной интеграции
оставлен бюджет 30 секунд. В историческом прогоне до получения матрицы на наборе K=0
получалось 19 112.9 с за 30 секунд и 19 077.3 с за 150 секунд; эти значения нельзя
переносить на встроенную матрицу конфликтов.

Интеграция с приложением реализована отдельно в
[`api/modules/planning/`](../api/modules/planning/README.md): загрузка из локального
снимка, фоновая задача, отображение расписания и экспорт. Явная точка вызова/замены
алгоритма — `algorithm_adapter.solve(problem)`. Пакет `algorithm/` остаётся независимым
от FastAPI. Следующий этап — калибровать модель по сервису организаторов.
